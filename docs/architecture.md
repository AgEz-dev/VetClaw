# 架构说明

## 三层架构

Sentinel-Agent 分为三层，职责单一、可独立演进。

### 1. 接入层（FastAPI 工程网关）

对外提供 HTTP 接口与 SSE 流式通道。

- Pydantic V2 校验层：拦截非法入参与恶意 Prompt
- 异步并发与限流中间件（asyncio + 令牌桶）
- 全局异常捕获：TimeoutError 等异常优雅降级兜底

### 2. 调度层（自主 Agent 调度中枢，无第三方框架）

- ReAct 循环调度器：Thought → Action → Observation 状态机
- Tool-Calling 注册表：工具动态注册与 JSON Schema 自动提取，危险操作二次确认
- 滑动窗口记忆中枢：Token 预算控制，自动剔除旧轮次

### 3. 能力层（工具集）

- 本地代码 / 文件阅读与 AST 语法树切片（读操作）
- 知识库混合检索（BM25 + 向量召回，ChromaDB）
- 危险操作拦截器（写操作阻断并提示二次确认）

## 关键决策

### 1. 为什么不用 LangChain

- 框架重度黑盒，推理链路不透明，问题难以定位
- 框架抽象带来额外学习成本，掩盖 Agent 本质
- 原生实现依赖少、可控性强，便于理解原理与按需扩展
- 代价：需要自行处理状态管理、错误恢复与兼容性细节

### 2. 为什么选 ChromaDB

- 本地嵌入式向量库，零运维、无需独立服务
- Python 原生 API，与调度层集成简单
- 数据规模适合开发调试场景；需要横向扩展时可平滑迁移
- 代价：单机内存依赖，大规模场景需评估

### 3. 会话锁的边界

- 问题：多个并发会话共享 Agent 实例时，记忆与工具状态存在写竞争
- 方案：按会话加互斥锁，锁只保护共享可变状态（会话记忆、工具内部状态）
- 边界：纯计算与只读操作不加锁；锁粒度按会话隔离，避免全局锁造成吞吐瓶颈
- 代价：同会话内请求串行化，高并发下需要配合连接池与限流
